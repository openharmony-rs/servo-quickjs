# mozjs-on-QuickJS shim — runtime design

`mozjs/` is a crate named `mozjs` 0.26.7. It is swapped into Servo with `--config 'patch.crates-io.mozjs.path="…/servo-quickjs/mozjs"'`.

How it is built:
- It keeps SpiderMonkey's bindgen types (`mozjs/upstream-bindgen/jsapi.rs`, `gluebindings.rs`).
- Every SM function becomes a Rust function (generated by `mozjs/stub_bindings.py` at build time) that forwards to its QuickJS implementation in `mozjs/src/engine/`, or panics with "`NAME` is not implemented".
- The Rust layers of `mozjs` and `mozjs_sys` are copied from the 0.26.7 / 153.3.0-3 sources.
- The functions Servo reaches are implemented on QuickJS; the few representations that change are listed below.

## Values and pointers

- **`JS::Value` (`JSVal`)** uses QuickJS's 64-bit representation: 16 bytes, `{u: u64 | f64 | ptr, tag: i64}`. It is layout-compatible with `servo_quickjs::JSValue`.
  - SM's NaN-boxed 64-bit value can't be kept. Its 47-bit payload doesn't fit malloc'd QuickJS pointers on aarch64.
  - `jsval.rs` is rewritten on the QuickJS tags.
  - `PrivateValue(p)` is a `JS_TAG_FLOAT64` value whose bits are the pointer. It is never exposed to script.
- **`*mut JSObject`** is the QuickJS object pointer, so `ObjectValue(o)` = `{ptr: o, tag: JS_TAG_OBJECT}`.
- **`*mut JSString`** is a QuickJS `JSString*`. Ropes (`JS_TAG_STRING_ROPE`) are flattened before a `*mut JSString` is handed out (patch Q3).
- **`*mut JSContext`** points to the shim's per-runtime `Cx`: the QuickJS `JSRuntime`, the realm stack, the pending exception, and the autorelease pool. Natives, hooks and finalizers that run during a call into QuickJS reach the same `Cx` again, so the shim only takes shared references to it, and the state they change (pools, realm stack, microtask queue, hooks) is in cells (`engine/reentrant.rs`). The same holds for the data behind objects' opaque pointers (reserved slots, proxy and microtask data): accessors return shared references, and the fields that change are `Cell`s. HACKING.md ("Re-entrancy") has the rules.
- **`*mut JS::Realm`** and **`*mut JS::Compartment`** both point to a `RealmData`: the QuickJS `JSContext` plus the global. There is one compartment per realm.

## Ownership: counted storage plus a per-task pool

Rule: anything that can outlive the current task holds a reference count; anything on the stack is kept alive by the pool.

| mozjs / Servo type | QuickJS semantics |
|---|---|
| Raw `JSVal`, `*mut JSObject`, `Handle`, `MutableHandle` | Not owning. |
| Values the shim returns to Rust (results, out-params), and `Rooted`/`rooted!` initialisation | Dup the value into the **autorelease pool**. Servo drains the pool between tasks: in `ScriptThread::start`, and at the start of each `run_worker_event_loop` call. Each call from QuickJS into Rust (`call_native`, proxy traps) also drains back to its entry mark when it returns, like SpiderMonkey roots dying with the native's frame, so loops calling natives don't grow the pool. So do the promise hooks that call the embedder's incumbent-global trap (patch Q32's, and `enqueue_microtask`), so `then()` and `await` don't add an entry each. Servo (`js-quickjs`) opens an `AutoreleasePoolScope` for each microtask of a checkpoint, so a long chain of microtasks in one task doesn't keep every finished job alive; this is safe because roots hold no references and the loop's roots are written before they are read in each iteration, and what a job leaves for later is counted (`Heap`, `Dom<T>`). Roots therefore rely on the pool, and SpiderMonkey-legal ways of writing to them (`as_mut_ref`, `.ptr`, out-parameters) stay valid until the drain; `tests/qjs_root_contract.rs` keeps them working. |
| `Heap<T>`, reserved slots | Counted: the `Heap*WriteBarriers` dup the new value and free the old one; `Drop` frees; `trace` marks it. |
| `AddRawValueRoot` / `PermanentRoot` | Counted, never marked. |
| Realm pointers cached by shim objects | Counted on the realm's context and marked (Q15); realm-stack entries counted, not marked. |
| Global's `ProtoOrIfaceArray` entries | Counted: every store and the global's finalizer go through `<*mut JSObject>::post_barrier`, i.e. `HeapObjectWriteBarriers`; marked by `trace_global`. |
| Servo `Dom<T>` (feature `js-quickjs`) | Counted on the target's JS object (`from_ref`/`clone` retain, `Drop` releases), and marked by the existing `trace`. Still one pointer, see "Finalization" below. A `Dom<T>` made before its target is reflected (a `DissimilarOriginWindow`'s `WindowProxy`) records a pending count, taken when the reflector is set. |
| Servo `DomRoot<T>` | A `Dom<T>` inside, so counted. |
| The last count of an object, released by Rust (`release_object`) | Moved to the pool instead, so the object is freed when the pool drains, after the current native call or task. Freeing it at once ran finalizers while Servo held borrows (a WebGL framebuffer's attachments `RefCell`, released from inside a framebuffer method). In a cycle collection the object may be part of the cycle being freed, and goes with it. |
| `Reflector` | **Uncounted**: `set_jsobject` bypasses the barrier, and finalization clears it; under the feature `Reflector` has a `Drop` that clears it too, for reflectors owned by Rust (`Rc<Promise>`). A counted self-reference would never be marked (`Reflector`'s trace is a no-op) and would leak every DOM object. Uncounted, DOM objects are freed promptly by refcounting. `repr(C)` under the feature, so `object` comes first. |
| `Trusted<T>` | The live-references table entry holds one count from creation until `sweep_live_references` (end of each task) drops entries whose `Trusted` values are gone. Releasing in `Drop` is not possible because `Trusted` values may die on other threads. |
| `Rc<T>` fields | Traced only while `strong_count == 1`. A shared `Rc` would be traced once per owner but its contents counted once, and the cycle collector would free live objects. Shared contents act as external references instead: they may leak, but are never freed early. |

**Finalization.**
- When the cycle collector frees a cycle, B's finalizer may free B's Rust struct before A's finalizer drops A's `Dom<B>`. `Dom<B>` reaches B's JS object through B's `Reflector`, which lives in B's Rust struct.
- So reflectors are registered in a per-thread map (Rust address → JS object) when reflected, and unregistered by the finalize hooks before the Rust struct drops. The hooks run the drop with a `FINALIZING` flag set.
- While finalizing, `Dom::drop` looks up the map: a missing entry means the target died in the same collection, and there is nothing to release.
- Outside finalization the target is alive (the `Dom` holds a count), so its reflector is read directly.
- `JS::RuntimeHeapState` is `MajorCollecting` while the cycle collector frees a garbage cycle (Q23), and `Idle` otherwise, also while an object whose count dropped to zero is finalized: its references are alive. Servo's `during_gc_collection()` guards (e.g. `LoadBlocker::drop`) then skip work on objects that die in the same cycle; without it a `Trusted<Document>` was made for a document of the cycle, and swept after it was freed.

Why the pool is safe:
- Under SM, an unrooted value dies at the next GC, which can happen at any `CanGc` point.
- Under the pool, every value Rust has touched lives until the pool drains back past it: at the end of the task, when the native call, proxy trap or promise hook that took it returns, or when the `AutoreleasePoolScope` it was taken in is dropped.
- A drain at a return is like SM roots dying with the native's frame; the shim duplicates what it hands back to QuickJS (return values, out-parameters) before draining.
- So code that is correct under SM is also correct here, except for a root written after a drain's mark and read after the drain, such as a root declared before an `AutoreleasePoolScope` and written inside it: under SM it stays valid, here it dangles. Servo's microtask checkpoint and `tests/qjs_root_contract.rs` write such roots before reading them in each iteration.

The cost is memory: values stay alive until the end of the task. A build with `QJS_POOL_STATS=1` measures what the pool holds, by API function and by what became of each value (`engine/pool_stats.rs`, `tools/pool_stats.py`).

**Runtime teardown.** Servo destroys the runtime while Rust still holds counts (`ScriptThread` fields, `Trusted` entries). As in SpiderMonkey, destroying it frees every object (patch Q11) and every realm (Q15) and runs their finalizers; afterwards `Heap` barriers and `release_object` do nothing, and Servo's `Dom::drop` checks `js::quickjs::runtime_alive()` before touching the reflector. Leak hunting uses the `dump-leaks` feature, which reports those objects instead of freeing them.

**Tracing.**
- The shim's `JSTracer` is `{rt, mark_func}`.
- `CallValueTracer`, `CallObjectTracer` and the other trace calls become `JS_MarkValue`.
- `JS_AddExtraGCRootsTracer` is a no-op, so Servo's `trace_rust_roots` never runs. Its roots are counted or pooled instead.
- Exactness is checked by the tracing verifier (`QJS_VERIFY_TRACING=1`, `engine/verify.rs`). It counts, per object, the references Rust holds through `Heap` barriers and `retain_object`. It aborts with a backtrace when one GC pass marks an object from Rust trace hooks more often than that. It also aborts when an object is freed while the autorelease pool holds it (patch Q12), which means some code released a reference it did not own. That check fires at the final release, not at the wrong one, but it names the object's class.

## Classes and objects

- **Each distinct `*const JSClass`** gets a QuickJS class ID, registered lazily in a `HashMap<*const JSClass, JSClassID>`.
- **The class's opaque pointer** is a shim-owned `ObjectData`: the reserved slots, counted `Cell<JSValue>`s, plus the `*const JSClass` and the object's realm. The slot count is `JSCLASS_RESERVED_SLOTS(flags)`. `DOM_OBJECT_SLOT` holds `PrivateValue(dom ptr)` as today.
- **QuickJS hooks map onto the SM class ops:**

  | QuickJS hook | Calls |
  |---|---|
  | `gc_mark` | marks the slots, then `cOps.trace(trc, obj)` |
  | `finalizer` | `cOps.finalize(gcx, obj)`, then frees `ObjectData` |
  | `call` | `cOps.call` / `cOps.construct` |

- **Resolve hooks** (`cOps.resolve`, used by globals): run lazily from an exotic `get_own_property` hook on global classes. Deleting a property that isn't defined yet runs the hook first, from an exotic `delete_property` hook, as SpiderMonkey's lookup does: Servo's interface objects are defined by the first resolution only, so `delete window.File` before any access would otherwise bring `File` back.
- **Assignments from Rust** (`JS_SetProperty`, `JS_SetPropertyById`, `JS_SetUCProperty`, `JS_SetElement`) ignore a failed assignment, like SpiderMonkey's (sloppy mode); only exceptions fail. `[PutForwards]` relies on it.
- **`Error.isError`** asks `DOMCallbacks::instanceClassIsError` about objects of DOM classes (Q27), so it is true for a `DOMException`.
- **`IsArrayObject`** and structured clone's transfer list check the builtin class, like SpiderMonkey's `GetBuiltinClass`: a JS Proxy of an array is not an array there (IndexedDB rejects it as a key), although `Array.isArray` sees through it.
- **Native functions** (every `JSNative`, e.g. bindings' `generic_method`/`getter`/`setter` with `JSJitInfo`) become objects of one `ShimFunction` class.
  - Its `call` hook receives `func_obj`, `this` (or `new.target`) and flags.
  - Its opaque data: `{native, jitinfo, realm, reserved slots for NewFunctionWithReserved}`.
  - The trampoline builds SM's `vp = [callee, this, args…]`, enters the function's realm, and calls `native(cx, argc, vp)`. It returns `dup(vp[0])`, or `JS_EXCEPTION` if the native returned false.
  - `name`, `length` and `prototype` are defined explicitly, and the prototype is `Function.prototype`.
- **Property specs:** `JSPropertySpec` / `JSFunctionSpec` arrays become `JS_DefineProperty` with `ShimFunction` getters, setters and methods. `JS_LinkConstructorAndPrototype` is plain property definitions.
- **Proxies** (`CreateProxyHandler(&ProxyTraps)`, `NewProxyObject`, `WrapperNew`): a `ShimProxy` class. Its `JSClassExoticMethods` call the SM traps, converting `PropertyDescriptor`, `ObjectOpResult` and `IdVector`.
  - Bellard implements all 11 exotic hooks, which covers `getPrototypeOf`, `setPrototypeOf`, `isExtensible` and `preventExtensions`.
  - Expandos live in a separate object (`GetProxyPrivate` / expando slot), because QuickJS consults ordinary own properties before the hooks.
  - DOM proxies (a `CreateProxyHandler` handler with a DOM class as extra, once `SetDOMProxyInformation` was called) get and set names that aren't indices from their prototype chain when the expando doesn't have them and the chain does, without calling the traps. This is what SpiderMonkey's JIT inline caches assume: Servo's shadows check is only the expando, and named properties come after the prototype's. `document.body`, `nodeList.length` or `el.style.color` skip the get trap's expando check, prototype walk and `JS_ForwardGetPropertyTo`, and the rooting each of them takes.
  - Whether a prototype chain has a name is cached (Q21) for the fast path and `JS_HasPropertyById`. The fast path checks the chain first, so a named item (`collection.name`, `dataset.x`) costs one cache lookup before the traps, instead of a walk. It only uses chains of ordinary objects: with an exotic object in the chain (e.g. a JS Proxy), the traps run and look the name up once, as with SpiderMonkey.
- **Id and object vectors** (`IdVector`, `StackGCVector<T>` handles): the handle points at a Rust `Vec<T>`. Entries are uncounted and kept alive by the pool, so they must not outlive the task.
- **Wrappers and compartments:** `JS_WrapObject` / `JS_WrapValue` are the identity, except that a Window global becomes its WindowProxy. `IsWrapper` is true only for proxies made by `CreateWrapperProxyHandler` (the WindowProxy), which is what Servo's `private_from_proto_check` expects. There are no compartment checks: documents of one site share an event loop and runtime, and their cross-origin checks are only Servo's WindowProxy and Location proxy handlers.
- **Cross-origin property holders:** Servo caches one per accessing realm and WindowProxy or Location (`ensure_cross_origin_property_holder`) with `NewWeakMapObject`, `GetRealmKeyObject` and `Get/SetWeakMapEntry`, which serve only that cache:
  - the map is an id, never reused;
  - the key is the accessing realm's private key object, which its global holds;
  - the holder is kept by that key object.

  No script runs, and the WindowProxy doesn't keep the accessing realm alive, as a QuickJS WeakMap would (its values live as long as the map). The entries of a freed map are freed at the realm's next use of the cache, or with the realm. On real WeakMaps `Get/SetWeakMapEntry` call the realm's original `WeakMap.prototype.get` and `set`.
- **Builtins:** the shim's own operations call the builtins a realm was created with, taken before any of its scripts run (`intrinsics.rs`), as SpiderMonkey runs its builtins directly. This covers the Map, Set, WeakMap, Date and RegExp helpers, the self-hosted `Array` iterators, `JS_ValueToObject`, `JSON.parse` with a reviver, and the symbol descriptions and `Symbol.keyFor` of `JS_ValueToSource` and accessor names. Script that replaced `Map.prototype.get` or `globalThis.Object` doesn't run inside them.
- **`JS_TransplantObject`:** swaps the proxy data of the two proxies, so the original object keeps its identity and gets the new target.
- **Proxy prototypes:** a proxy with a static prototype keeps it in its QuickJS shape (so `JS_GetStaticPrototype` works); one with a lazy prototype (the WindowProxy) has get/set prototype hooks. Callable proxies are not supported.
- **Realm lifetime:** a `RealmData` is owned by its QuickJS context and freed by the context finalizer (Q15).
  - The global, objects of SpiderMonkey classes, native functions and proxies hold a counted reference to their realm's context and mark it from `gc_mark`.
  - The context holds its global and WindowProxy. QuickJS's own functions, proxies and FinalizationRegistries hold and mark theirs.
  - Realm-stack entries hold an unmarked count.
  - So the cycle collector frees a realm with its global once nothing outside the engine refers to them, after the global's finalizer has run.
  - Servo itself must not keep a Window alive through a permanent root. `document.fonts`' ready promise and the `FontFace` status promises are such roots (`Rc<Promise>` → `AddRawValueRoot`), so Servo's `js-quickjs` changes release them when a window is torn down.

## Realms and globals

- **`JS_NewGlobalObject(cx, clasp, …)`** creates a new QuickJS `JSContext` whose global object is an instance of `clasp` (patch Q1).
- **Global `this`** is a separate value, the WindowProxy, set via patch Q2.
- **Entering a realm:**
  - `JSAutoRealm`, `EnterRealm` / `LeaveRealm` and `AutoRealm` push and pop the realm stack in `Cx`.
  - `GetCurrentRealmOrNull` and `CurrentGlobalOrNull` read the top of that stack.
- **The realm of a DOM object** is stored in `ObjectData`, because QuickJS objects don't record their realm.
- **Other objects** (e.g. promises QuickJS creates): functions, promise resolving functions and proxies know their realm (patches Q6, Q18, Q13); any other object takes the realm of the first prototype whose realm is known, or of the realm whose `Object.prototype` ends its chain; else the current realm.

## Exceptions

- The pending exception lives in QuickJS (`rt->current_exception`).
  - `JS_IsExceptionPending` → `JS_HasException`.
  - `JS_GetPendingException` → `JS_GetException` followed by re-throwing it (peek semantics).
  - `JS_ClearPendingException` → `JS_GetException` and free the result.
- **Uncatchable errors** (from the interrupt callback) map to SM's "uncatchable" state, where the native returns false with no exception pending. As in SpiderMonkey and HTML's "abort a running script", a terminated script runs no more JS: QuickJS's built-ins that catch exceptions (promise executors, resolving functions and jobs, `Promise.all` and friends, async functions and generators, async-from-sync iterators, module loading) leave it pending instead of rejecting a promise, and closing an iterator runs no `return()` and keeps it uncatchable. A terminated async function or generator settles nothing more, as in SpiderMonkey. Module evaluation follows SpiderMonkey instead: a terminated module is rejected with `undefined`, so `ModuleEvaluate` still succeeds with a rejected promise, and the other modules waiting for the same asynchronous dependency still run (Q37).
- **Error reports:** `JS_ErrorFromException` and `ErrorInfo` are filled by reading `fileName`, `lineNumber` and `columnNumber`, which Bellard sets on syntax errors, otherwise from the first frame of `stack`. Values that are not Error objects are reported at their throw site (patch Q9). `exnType` is always `JSEXN_ERR`.
- **Saved frames** (`CaptureCurrentStack`, `JS_StackCapture_*`, `BuildStackString`) are objects of a shim `SavedFrame` class built from Q9 frames. QuickJS's columns point at the call's `(`, so they differ from SpiderMonkey's.
- **Scripted caller private:** `JS_GetScriptedCallerPrivate` maps the innermost frame's file name to a script or module private (see "Modules").
- **eval of an object** asks `codeForEvalGets` for its code (Q22), so `eval(trustedScript)` evaluates the script after the CSP and Trusted Types checks, which see the object as the argument. For `Function`, the checks see the source text `function anonymous(…\n) {\n…\n}`, as with SpiderMonkey.
- **Known gaps:** code from `new Function` reports its file as `<input>` (SpiderMonkey: `page.html line N > Function`). `stack` stays an own data property of QuickJS's errors, as in V8; `Error.prototype.stack` is also an accessor, as in SpiderMonkey (Q29), so a `DOMException` has a `stack` (an empty string, as with SpiderMonkey). A structured clone of an error therefore has its stack as an own property, where SpiderMonkey keeps it in an internal slot.

## Microtasks

- As in SpiderMonkey 153, the microtask queue belongs to the context, and Servo runs it at its microtask checkpoints (`HasAnyMicroTasks`, `JS_DequeueNextMicroTask`, `RunJSMicroTask`). Servo's own microtasks are entries of the same queue (`EnqueueMicroTask` with a private value), so their order with promise jobs is kept. Servo's `JobQueue` (`CreateJobQueue` traps) supplies the incumbent global (`getHostDefinedData`); the shim's `JS::JobQueue` is mozjs's `RustJobQueue`, whose `draining` flag Servo reads.
- **Patch Q4** adds an enqueue hook to QuickJS. Each promise job (job function + args + realm) becomes an object of a shim `MicroTask` class, SpiderMonkey's "JS microtask", and is queued.
- `JS_ExecutePendingJob` is not used.
- A `MicroTask` holds the job function and its counted arguments (in a Rust `Vec`, so a page's setters on `Array.prototype` can't run); its realm, the execution global, is the context that enqueued the job: the realm of the reaction's handler or thenable's `then` (patch Q17, NewPromiseReactionJob), which Servo uses as the job's entry realm. Promise resolving functions run in the realm that created them (Q18), so a rejection is reported to that realm's global. It runs once and then releases the arguments. The incumbent global (`getHostDefinedData`) of a reaction job is taken when `then()` or `await` creates the reaction (HostMakeJobCallback, patch Q32), as in SpiderMonkey 153; that of a thenable job when it is enqueued. It is kept in the `MicroTask`. Each job is enqueued with SpiderMonkey's promise for it (`MaybeGetPromiseFromJSMicroTask`, Q30): the promise `then()` created for a reaction job (none for `await`), the promise to resolve for a thenable job. Promises keep Servo's user input state, and `then()` copies it to the promise it creates, so a promise created during user interaction runs its reactions as user interaction, as in SpiderMonkey (e.g. `xrSession.end().then(() => navigator.xr.requestSession(…))` after a click).
- FinalizationRegistry jobs stay on QuickJS's internal list (they are enqueued during GC), so they never run while a host queue is installed.
- **Interrupts:** `JS_AddInterruptCallback` callbacks run from QuickJS's interrupt handler; one returning false terminates the script uncatchably. `JS_IsExceptionPending` / `JS_GetPendingException` then report no exception, as in SpiderMonkey. QuickJS polls for interrupts on every call, built-in and native callees included, where SpiderMonkey checks only in script. So while the promise operations Servo expects to succeed (`NewPromiseObject`, `CallOriginalPromiseResolve`/`Reject`, `ResolvePromise`/`RejectPromise`) and `ModuleEvaluate` run only built-ins and natives, a requested interrupt stays pending, and QuickJS polls again at its next check (Q36, Q37). Script they run, such as a `then` getter or an executor, is interrupted as usual.
- **Unhandled rejections:** `SetPromiseRejectionTrackerCallback` → `JS_SetHostPromiseRejectionTracker`. `mutedErrors` is that of the innermost scripted frame's script, as in SpiderMonkey (`JS_EVAL_FLAG_MUTED_ERRORS`, Q16).

## Modules

- **Module records** are objects of a shim `ModuleObject` class holding one count of their QuickJS `JSModuleDef`. QuickJS's context also keeps every module until the realm dies. JSON modules are C modules with a `default` export.
- **Loading** follows SpiderMonkey 153 (ECMA-262 LoadRequestedModules). `CompileModule1` compiles with `JS_EVAL_FLAG_NO_RESOLVE` (patch Q7), so the requests are not loaded. `LoadRequestedModules` walks the graph with a GraphLoadingState object (the payload) and calls Servo's load hook for each request not in the requesting module's [[LoadedModules]]; Servo answers, now or after a fetch, with `FinishLoadingImportedModule` or one of the `…Failed` variants. Each module record keeps its [[LoadedModules]] (counted, marked) and its request objects (made once per request, so the hook sees the same object each time; each knows its module and index). `ModuleLink` calls `JS_LinkModule`, which resolves each request from [[LoadedModules]].
- **Referrers** are `JSScript`s: a module's is its code (patch Q31), and `JS_GetScriptPrivate` of a module's code returns the module's private, as in SpiderMonkey. `JS_GetGlobalFromScript` returns the global of the realm the code was compiled in (Q35).
- **Privates:** a JavaScript module's private lives in its `JSModuleDef`, a classic script's in QuickJS's record of the script (patch Q16), which every function of the script shares. Eval and `Function` code share the record of the code that created them, as SpiderMonkey copies the introducer's private. import.meta, import() and `JS_GetScriptedCallerPrivate` read the running function's record, never the file name: inline scripts and modules of one document share the document URL. `SetScriptPrivate` and `SetModulePrivate` take a reference through Servo's add-ref hook and release the value they replace, as SpiderMonkey's `ScriptSourceObject::setPrivate` does. The reference is released when the script's last function is freed, or with the module (Q34), which lives as long as its realm. `ClearModulePrivate` releases it early.
- **import.meta** is populated on first use by Servo's metadata hook, which receives the module record. **import()** calls the load hook synchronously, with the code of the calling script or module as referrer (Q31) and the import() promise as payload; Servo settles it (`FinishLoadingDynamicImportedModule`, then its own ContinueDynamicImport), and a failure rejects it.
- **Evaluation:** `ModuleEvaluate` returns QuickJS's evaluation promise. `ThrowOnModuleEvaluationFailure` throws the rejection reason and marks the promise handled. A pending promise (top-level await) is not a failure here; SpiderMonkey reports it as an undefined exception. Errors after an await surface as unhandled rejections.
- **Import attributes:** an unsupported key fails the load with a SyntaxError for static imports and rejects import() with a TypeError; types are `json`, `css` and `text` (SpiderMonkey's default prefs), anything else is `Unknown`, which Servo rejects with a TypeError, as with SpiderMonkey.
- **Synthetic modules** (JSON, and CSS and text modules via `CreateDefaultExportSyntheticModule`) are C modules whose only export is `default`; they have nothing to load.
- **Not implemented** (Servo does not call them): `GetModuleObject`, `GetModuleForNamespace`, `GetModuleEnvironment`, source-phase imports, and `FinishLoadingImportedModule` with an import() promise as payload (SpiderMonkey's ContinueDynamicImport; Servo calls `FinishLoadingDynamicImportedModule` and continues itself). The load hook gets no source positions (line 0, column 1).

## Strings

- `JS_GetLatin1StringCharsAndLength`, `JS_GetTwoByteStringCharsAndLength` and `JS_DeprecatedStringHasLatin1Chars` read QuickJS's 8- or 16-bit buffers directly (patch Q3 exports an accessor).
- `JS_NewStringCopyN`, `JS_NewUCStringCopyN` and `JS_NewStringCopyUTF8N` are copies.
- External strings (`JS_NewExternalStringLatin1`/`UCString`) are copies too, so they save no memory.
- Pinned atoms (`JS_AtomizeAndPinString(N)`) are kept by the pool, i.e. only until the end of the task. `PropertySpecNameToPermanentId` leaks one atom reference per call.
- SpiderMonkey's "emulates undefined" (`document.all`) is not handled in ToBoolean or typeof.

## Intl

`engine/intl.rs` and `engine/intl/` implement an ECMA-402 subset over the OS's ICU: the NDK's on OpenHarmony, the system ICU on other glibc Linux. `build.rs` sets `qjs_intl` for these targets with the `intl` feature, and takes the suffix of a system ICU's symbols (`ucol_open_74`) from its headers. Elsewhere `Intl` is absent. It is installed on every new context and keeps no per-realm Rust state.

Date component options use a port of ICU 74's date pattern generator over a table generated from OpenHarmony 7.0's ICU data (`tools/gen_intl_patterns.py`), which OpenHarmony changed in places: China, for example, prefers 12-hour times. With that data, they match ICU for en-US, en-GB, the Chinese locales of the OpenHarmony data (zh-CN, zh-TW, zh-HK, zh-MO, zh-SG, zh-Hans-HK, zh-Hans-MO), ja, ko, de, fr, es, ru, en-CA and sv-SE. Other locales get their own style patterns and root's availableFormats, which can drop zero padding (pt-BR "7/10/2026", where ICU gives "07/10/2026").

Linux uses the same code and table, although its ICU has the pattern generator, so that component options give the device's results. Everything else comes from the system ICU's data: styles, numbers, collation and names. Where that data differs from OpenHarmony's, so does the result; on Ubuntu, zh-CN is 12-hour with component options but 24-hour with `timeStyle`.

As SpiderMonkey does for web compatibility, formatted dates and times have U+0020 for CLDR's U+202F and U+2009 ("3:05 PM", WPT ecmascript/locale-compat.html).

- Implemented: `Intl.NumberFormat`, `Intl.DateTimeFormat` (styles and component options), `Intl.Collator`, the `toLocale*String` methods, `localeCompare` and locale-aware case mapping.
- Missing: `Intl.PluralRules`, `RelativeTimeFormat`, `ListFormat`, `DisplayNames`, `Segmenter`, `Locale` and `formatRange`.

## Not supported

`Debugger` / devtools, WebAssembly, SharedArrayBuffer (already disabled in Servo), off-thread compilation, JIT options, and GC zeal.
Explicit resource management: QuickJS has no `Symbol.dispose` and `Symbol.asyncDispose`, so `GetWellKnownSymbol` returns null for them.
`JS_SetGCParameter` maps to `JS_SetGCThreshold` / `JS_SetMemoryLimit` where it makes sense; everything else is a no-op.
